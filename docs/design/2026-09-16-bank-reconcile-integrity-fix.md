# 银行对账第一批准确性修复

## 1. 财务业务规则

- 同一业务不能确认匹配给多条银行流水，收入和支出执行相同约束。
- 先收集完整范围的候选；只有双方唯一且金额按整数分相等时自动确认。
- 多条流水争用同一等额业务时均保留为 DUPLICATE，不按流水先后任意确认。
- AMOUNT_DIFF、DUPLICATE 仅表示待核查线索，不占用业务；已确认业务不再作为其他流水的金额差异候选。
- 没有出现在任何匹配/差异/候选结果中的范围内业务，必须输出 BIZ_ONLY；存在同日同账号银行流水不能代替实际关联。
- 无流水号缴费保留为待核查，禁止凭金额或姓名自动补配。UNKNOWN 收费方式也不作为已建立认领来源关系的证据。
- BIZ_ONLY 不等于银行未到账。不明款认领应核查原不明款来源，不能重复作为新增银行收入。
- 已认领不明款的来源关联、人工确认、跨期匹配、拆分合并属于后续批次，本次不实现。

## 2. 数据库

复用银行流水和对账结果表，无新增字段、表或迁移 SQL。保留原软删除、事务、账套隔离与审计机制。

业务待核查分页增加 reconcile_id 排序兜底，避免同日、空流水号记录分页顺序不确定。

## 3. 业务流程

候选收集 → 汇总等额候选的双向占用情况 → 确认双向唯一关系 → 展示未确认候选和金额差异 → 输出尚未展示的业务单边项。

页面保留银行流水主表，新增“业务待核查”抽屉，按当前账套、年度和所选日期查询最近一次保存的 BIZ_ONLY 结果，支持精确跳转原业务及独立导出。金额差异和重复候选仍从银行流水主表查看，避免重复生成业务单边项。

## 4. 接口

复用 `/caseFund/bankReconcileRun`、现有后台对账任务及 `/caseFund/bankReconcileList`。
抽屉请求固定 `status=BIZ_ONLY`，携带日期范围、页码和页大小；权限沿用 `case_fund:view`，跳转按业务菜单权限控制。

## 5. 字典

继续使用 MATCHED、AMOUNT_DIFF、DUPLICATE、BANK_ONLY、BIZ_ONLY；不增加隐含确认状态。

## 6. 实现与验证

- 匹配器统一收入、支出规则，并移除“银行候选存在即压掉业务差异”的反查路径。
- 仓储范围查询保留无流水号缴费；预取仍为四组窄字段查询。
- 抽屉使用独立组件；切换账套、日期或关闭时丢弃过期响应，导出固定筛选范围并检查分页总数及重复行。
- 新增完整性回归测试覆盖重复退付、金额差异抢占、重复候选抢占、流水顺序变化、缺失流水号及业务侧差异遗漏。
- 新增 Vue 组件运行测试，覆盖过期响应、超过一页的导出、切换账套中止导出和关闭清理。
- 相关后端测试、前端测试及 `npm run build` 通过。
- 当前配置库五月只读试算：银行 1532 条、缴费 648 条、不明款 35 条、退付 873 条；银行状态与已保存结果一致，业务单边项 26 条（原保存 2 条），业务完整性与唯一占用断言通过。试算未写库。
- 浏览器已验证待核查抽屉展示旧结果及精确跳转不明款原记录；没有执行自动对账写入。

## 生效和交付

本次后端业务文件只有 CaseFundBankReconcileMatcher.php、CaseFundBankReconcileRepository.php，按项目约定归档到 server-update/2026-09-16/。仓储文件原有的用途筛选改动保持原样。

前端包含新增抽屉组件及银行对账页接入，已构建到 frontend/dist；生产发布需同步更新前端构建产物。没有生产部署。

历史结果需在更新后重新执行所需日期范围的自动对账才会补齐。认领来源关联仍待第二批，不能把这批修复当作认领款自动对账已经完成。
